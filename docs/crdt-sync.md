# 自動保存・同期

## ライブラリの比較

| 候補 | 特徴 | このアプリでの判断 |
| --- | --- | --- |
| [Yjs](https://docs.yjs.dev/api/document-updates) | Y.Textによる文字列編集。更新は順序に依存せず、重複適用も可能。通信方式を選べる | 採用。textarea、HTTP、既存の認証・SQLiteを利用できる |
| [Automerge](https://automerge.org/docs/tutorial/network-sync/) | 文書の履歴と同期プロトコル、Repoによる保存・通信アダプター | 有力な候補だが、今回は既存のPythonバックエンドにYjs互換のpycrdtを組み込む構成を選択 |

フロントエンドはYjsとy-indexeddb、バックエンドは[pycrdt](https://y-crdt.github.io/pycrdt/api_reference/)を使用する。公開同期サーバーや外部SaaSに日記を送信しない。

## 動作

- 日記の日付ごと、およびテンプレートごとに独立したY.Textを持つ。変更箇所の削除・挿入を行い、全文を置換しない。
- 入力後400msで送信し、2秒間隔とフォーカス復帰・オンライン復帰時にも双方向同期する。日本語IME変換中はサーバー更新の適用を保留する。
- POST `/nikki/{date}/sync` または `/template/sync` でYjs v1形式のバイナリー状態を交換する。単一画面では同時リクエストを1件に限定し、送信中に追加された編集は次の送信に含める。
- IndexedDBに更新を保存する。通信失敗後も編集を維持し、自動再試行する。画面を離れる際にも最終送信を試みる。未送信のまま離れた日付の変更は、その日付を再表示した際に再送する。
- ブラウザーを再起動した場合、キャッシュを開く前にオンラインでユーザーを確認する。完全にオフラインの状態でのアプリ起動には対応していない。ブラウザーのサイトデータを削除すると未送信の変更も削除される。
- `/sync-identity` で確認したユーザーIDとバックエンドURLでキャッシュを分離する。同期APIは認証Cookieと `X-Sync-User` の一致を確認し、別タブでログイン先が変わった場合の誤送信を拒否する。
- SQLiteの `BEGIN IMMEDIATE` で、最新状態の読み込み・マージ・CRDT状態と本文の保存を直列化する。複数ワーカープロセスでも同じSQLiteファイルを使用する必要がある。
- 全文削除後もCRDT履歴を保存する。古い端末が再接続しても、削除済み本文が復活しない。
- ZIP取り込みによる置換と日次テンプレート追加も、同じCRDT状態を更新する。

画面には「同期済み」「未同期の変更があります」、失敗時の再試行状態を表示する。「同期済み」はサーバーが送信済み変更を永続化した状態であり、別の端末にも表示されたことまで保証する表示ではない。

同じ箇所を同時に書き換えた場合、双方の文字列が並ぶなどCRDTのマージ結果になる場合がある。文章としての意味や編集者の意図を自動判定する仕組みではない。

## 習慣キーワードの同期

習慣は POST `/habit/v2/sync` で同期する。一覧のJSONをY.Textで編集すると、クライアントの入力とサーバーのID・件数の書き戻しが文字単位で混ざり、JSONの破損や行の消失が発生する。そのため、習慣は行をキーとする [Y.Map](https://docs.yjs.dev/api/shared-types/y.map) を使用する。

- `habits` の各行に固定の同期IDを割り当て、`keyword`、`isPublic`、表示順を個別に保存する。空の追加行も同期・端末内保存の対象にする。
- `habitMetadata` にサーバーがDBのIDと累計日数を書き込む。入力欄のReactのキーは同期IDを使い、DBのIDが確定しても変えない。
- DBの `habit_keyword.sync_id` で行を対応付け、同じ単語の複数行にも別のDB IDを維持する。追加時は直ちに同期を開始し、空行もDBへ保存して応答からIDを表示する。キーワードの変更、空欄への変更、リトライでも既存行のIDを再採番しない。
- 行の削除はMapから削除する。削除前の端末からその行の編集が届いても復活させない。別の行や別の項目への同時編集はマージし、同じ項目への同時編集はY.Mapの競合解決結果に収束する。
- キーワードを変更した行の累計は0に戻し、次の日次バッチで再計算する。空欄はカウントしない。

公開設定が有効な行は GET `/{user_name}/habit/{HabitKeyword_id}` で認証なしに `{"total_count": 7}` の形式で取得できる。`user_name` はDBの `User.username` と照合する。非公開・存在しないID・ユーザー名が一致しない場合は404を返す。応答はキャッシュしない。

起動時に `sync_id` 列とユーザー内の同期IDの一意インデックスを追加する。最初のv2同期時にDBに保存済みの行から新しい文書を作成し、DB IDと累計日数を引き継ぐ。旧JSON文書と旧IndexedDBキャッシュは削除しない。旧形式の未送信編集は自動移行しないため、更新前に必要な入力を控えて再入力する。破損した旧JSONを再適用することもない。

バックエンドとフロントエンドを更新し、バックエンド再起動後、各端末の画面を再読み込みする。旧 POST `/habit/sync` は提供しない。習慣の同期先は POST `/habit/v2/sync` のみで、更新前の画面からは同期できない。日記・テンプレートの同期形式とキャッシュは変更しない。

## 導入

1. 既存のSQLiteデータベースをバックアップする。
2. バックエンドで `pip install -r requirements.txt` を実行し、新しいコードで再起動する。
3. フロントエンドで `npm ci` と `npm run build` を実行し、成果物を配置する。
4. 各端末の画面を再読み込みする。

起動時に追加テーブル `collaborativedocument` を作成する。既存の日記・テンプレートは最初の同期時に、サーバー側で一度だけCRDT化する。従来の本文カラムとGET APIは引き続き利用できる。旧 PUT `/nikki/{date}` と PUT `/template` は提供しない。保存には POST `/nikki/{date}/sync` と POST `/template/sync` を使用するため、バックエンドとフロントエンドを一緒に更新する。移行前から開いている画面の未保存テキストは、再読み込み前に控えておく。

現在は構成の単純さを優先して毎回CRDTの全状態を交換している。リクエスト上限は8MiB。長大な編集履歴では通信量が増えるため、その場合はstate vectorによる差分交換やWebSocketへの拡張を検討する。CRDTテーブルだけを削除・再生成すると既存端末の履歴と整合しなくなるため、本文とCRDT状態は一緒にバックアップ・復元する。

## 検証

- `cd frontend && npm test`：古い端末の編集、IndexedDB復元・再送、日本語IME、遅延応答と日付切り替え。習慣の空行保持、重複キーワード、ID・入力フォーカスの維持、遅延応答中の追加・編集・削除。
- `cd frontend && npm run build`：TypeScriptと本番ビルド。
- `cd backend && python -m unittest discover -v`：既存データ移行、同時更新、重複送信、削除、Unicode、ZIP・テンプレート、認証分離、実際のYjsとpycrdtの相互変換。習慣のスキーマ移行、IDの維持、重複キーワード、古い端末からの再送、バッチとの同時編集も検証する。テスト用 `NIKKI_BOOK_SECRET_KEY` を設定して実行する。Node.jsとフロントエンドの依存関係も必要。

バックエンドのテストは一時SQLiteファイルを使用し、実際の日記データにはアクセスしない。
